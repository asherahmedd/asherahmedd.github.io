CDS Extraction and CDC in SAP Datasphere

Configuration and validation of delta-enabled ABAP CDS extraction using SAP Datasphere replication flows.

ABAP CDS · CDC · Replication Flows · Initial and Delta · Monitoring

Scope and supported approach

This article covers CDS-based extraction from a compatible SAP S/4HANA or ABAP source into SAP Datasphere local tables. The preferred ingestion approach for eligible replication scenarios is a Replication Flow; downstream transformations can be modeled separately using SQL/graphical views or transformation flows.

CDC describes how changes are detected on the source. Initial and Delta is a replication-flow load type. Neither setting alone makes an unsupported source object delta-capable.

Before implementation: Confirm the source release, SAP notes, extraction eligibility, supported connection and load modes, and a stable primary key. SAP Note 3297105 is referenced by SAP for replication-flow considerations.

For ABAP CDS CDC, the source extraction framework uses change logging based on underlying tables and their mapped keys. ODQ/ODP is relevant to supported ABAP extraction scenarios; the precise internal processing path varies with the connection and SAP source release. Do not treat all replication modes as the same implementation.

1. Prepare the CDS extractor

  1. Choose a suitable extraction object.

    Prefer an SAP-delivered extraction-enabled CDS view where available. For a custom view, confirm source release, keys, cardinality, and that the view type is supported for the intended extraction method.

  2. Enable extraction.

    For supported custom ABAP CDS views, use @Analytics.dataExtraction.enabled: true.

  3. Configure the delta method.

    For a suitable single-table projection, automatic CDC mapping can be used. For supported joins, explicitly map underlying table keys and roles. Do not assume CDC works for arbitrary joins, unions, aggregations, or parameterized views.

  4. Activate and verify availability.

    Verify extraction metadata and the source object exposed through the appropriate connection context. Where applicable, use I_DataExtractionEnabledView to identify eligible extraction views.

Automatic CDC — simplified annotation pattern
@Analytics.dataExtraction.enabled: true
@Analytics.dataExtraction.delta.changeDataCapture.automatic: true

define view entity ZI_EXTRACT_EXAMPLE
  as select from zsource_table
{
  key key_field,
      business_field,
      changed_at
}

Illustrative only. Replace the source and fields and validate supported CDS syntax, permissions and CDC requirements in your SAP release.

Timestamp-based delta extraction (delta.byElement) is another annotation-based method where supported. It should not be described as trigger-based CDC: it uses a different change-detection approach, with specific limitations for deletions and timestamp accuracy.

2. Configure the Replication Flow

  1. Connection.

    Create or use a supported SAP S/4HANA / ABAP connection and verify access to the extraction object.

  2. Source.

    In Data Builder → New Replication Flow, select the source connection and extractor.

  3. Target.

    Select SAP Datasphere as target and configure the target local table and key columns. Confirm supported target settings and data-type mappings.

  4. Load type.

    Select Initial and Delta when the option is available for the source and target. Deploy and run. Use Initial Only for a deliberate snapshot; Delta Only is subject to stricter consistency considerations.

  5. Runtime.

    Choose delta interval processing or At Scheduled Time in Run Settings as appropriate. Review load frequency, thread limits, schedules and notifications rather than assuming continuous replication is necessary.

Important restrictions: SAP states that replication flows do not support input parameters. Sources without primary keys are only usable under documented conditions; manually defined target key columns must be unique and non-null.

3. Monitor and validate

Use Monitoring → Data Integration → Flows Monitor for flow status, run logs, loaded-record counts and replication-object details. For ABAP/ODP source scenarios, investigate the appropriate source-side monitoring when an extraction or subscription issue is suspected.

InsertCreate a source record and verify its arrival in the local target.
UpdateChange a non-key value and confirm the target is updated, not duplicated.
DeleteTest physical deletion only where the source and extraction method support it. Verify target behavior.
ReconciliationCompare key counts and selected values between source and target at a consistent time boundary.
Queue / runtimeCheck failed subscriptions, delayed processing, run logs and source authorization problems.
RecoveryDocument restart and reinitialization behavior before changing an active extractor.

Limitations and implementation decisions

AreaWhat to verify
Complex CDS logicAutomatic CDC is intended for supported simple projections. Supported joined views require explicit mappings; arbitrary unions and aggregations should not be assumed delta-capable.
View parametersReplication flows do not support input parameters. Create a compatible extraction layer or use a different supported approach.
Keys and grainStable keys are essential for inserts, updates and deletes. SAP documents special conditions for sources without primary keys.
Delta mechanismsTrigger-based CDC, timestamp-based delta and non-CDS delta sources have different behavior, prerequisites and delete handling.
Source compatibilityABAP/S/4HANA releases and required SAP notes differ; connection support and extraction contexts are not interchangeable.
Runtime frequencyDelta interval and scheduled execution must be configured based on available capabilities, workload and desired freshness.
TransformationSeparate complex joins or business rules from the extraction layer when they interfere with source delta compatibility.

In practice, start with a delta-capable source object at a stable grain, replicate it, and build the composite analytical model in Datasphere. This is an architecture preference, not a rule that every joined CDS view is unsupported.
