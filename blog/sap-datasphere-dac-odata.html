How SAP Datasphere Data Access Controls work with external OData applications

DAC looks simple in a diagram: assign users to regions and restrict their data. The difficult part begins when an external app calls the same view through an OData service. Which user is Datasphere actually authorizing?

Data security · OData v4 · OAuth 2.0Practical implementation notesNovember 2026

Where DAC really fits

I use Data Access Controls when the same analytical model is shared across teams, but users should only access their permitted business records. Instead of maintaining separate views for each region or business unit, a DAC defines the permitted row-level values and attaches those rules to the data model.

The key benefit is central enforcement. The external application can ask for sales data, but Datasphere decides which rows are visible to the authenticated identity. A page filter is not equivalent to DAC: a client-side filter can be removed, while a correctly applied DAC belongs to the underlying data access layer.

A concrete example: regional sales access

Suppose a single sales view contains orders from Riyadh, Jeddah and Dammam. The external dashboard is common to everyone, but the results are not.

Datasphere user identifierSalesRegionAllowed data
sales.west@example.comWESTJeddah region
sales.central@example.comCENTRALRiyadh region
sales.east@example.comEASTDammam region
sales.head@example.comWEST / CENTRAL / EASTAll three regions, via separate rows

This permissions entity is the foundation of the DAC. It must use the identifier format recognized by SAP Datasphere's identity configuration. The example addresses and regions are illustrative.

Configuring the DAC in Datasphere

  1. Prepare the permissions entity. Create a local table or view with the user identifier and business restriction fields. Ensure user IDs match the authenticated Datasphere identity, not merely the external application's username.
  2. Create a Data Access Control. Choose the permission entity, identifier column and relevant restriction criteria. For region-only access, use the SalesRegion column as the criterion.
  3. Map it to your model. Attach the DAC to the deployed SQL/graphical view or analytic model and map the permission criterion to its business field. The data model and permission entity must use matching values and data types.
  4. Expose the consumption model. For a supported view, enable Expose for Consumption, deploy it and generate the OData request from Datasphere's editor. Analytic models have their own consumption behavior. Confirm the selected asset type and API exposure method support the intended DAC scenario in your tenant.
  5. Authorize and test. Confirm consumption privileges, OAuth identity, permission rows and response data in a separate consumption context. Validate both an allowed and a disallowed region.

The part that matters most: OData identity

A DAC does not read a parameter such as ?region=WEST and treat it as authorization. It evaluates permissions based on the identity Datasphere receives. This becomes important when your consuming app has its own login system.

Individual user authentication

When the integration propagates an individual user's authorized identity to Datasphere, the DAC can evaluate that user's permissions entity rows. West and East users can receive different results from the same exposed view.

Per-user restriction
Shared technical identity

With a shared technical identity, the DAC evaluates that technical account's permissions. Two people using the same backend account generally receive the same DAC scope, even if the app knows their names.

Shared service scope

For example, imagine that Ahmed and Sara log into the same React application, while a Node.js backend uses a single OAuth technical client to request data. If the technical identity is allowed to read WEST and EAST, both app users may be able to retrieve both regions unless the backend implements its own properly enforced authorization. Passing a user's email in a request header does not, by itself, impersonate that user in Datasphere.

The shared identity trap
AhmedApp account: WEST

↓ Both requests use one OAuth technical identity ↓

Use a supported user-propagation flow when per-person Datasphere enforcement is required, or design a trusted backend authorization layer and restrict technical credentials to the minimum necessary scope.

Consumption API example

Once the view is deployed and exposed, use the OData URL generated by Datasphere's editor. The following is illustrative; object paths and entity names depend on your tenant and model.

GET <OData URL generated in SAP Datasphere>?$top=20
Authorization: Bearer <access_token>
Accept: application/json

The $filter, $top and $select parameters control the requested dataset and response shape. They do not grant access beyond DAC permissions. Use the generated endpoint rather than hand-writing a path for a production integration.

What I check before calling a DAC implementation complete

For production integrations, I test the complete path—not only whether the DAC object deploys successfully. That means verifying the identity in the token, permissions data, column mapping, consumer role, OData endpoint and the final records delivered to the application. Also test the denied scenario, where the user has no region access.

In a multi-tenant AI or conversational analytics application, this matters even more. If an LLM chooses which API to call, the authorization still belongs in Datasphere or the trusted backend, never in the prompt or user interface. Agents may decide what information they need; they must not decide what a user is entitled to see.

My preferred design principle: Model once, secure at the appropriate data layer, then validate the same security behavior through the actual integration identity. OData transports data; DAC decides which data the identity is permitted to receive.
