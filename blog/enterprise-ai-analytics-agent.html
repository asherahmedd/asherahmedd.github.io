1. What the solution actually is

A custom analytics agent is an application that interprets a business question, identifies the correct approved data product, retrieves only the necessary records or aggregations, and returns a traceable answer. It is not a chatbot with unrestricted access to the database.

SAP Datasphere acts as the governed enterprise data and semantics layer. The AI service sits outside Datasphere and provides natural-language interpretation, tool selection, response generation, and user experience. SAP S/4HANA, other SAP applications, SQL databases, files, or APIs can feed Datasphere through supported source-specific integration paths.

Architecture boundary: A custom LLM application, retrieval middleware, and its user interface are application components—not native SAP Datasphere features. SAP Datasphere supplies modeled, permissioned, consumable data assets. An AI model does not automatically understand Datasphere semantics simply because an OData endpoint exists.

Typical requests

  • “What were net sales last month, compared with the previous month?”
  • “Show the top ten customers by net revenue for Region A.”
  • “What is the current inventory position by material group?”
  • “Which purchase orders are overdue?”

Recommended cross-functional KPI packs

A useful analytics agent should not stop at a single sales chart. In practice, the most effective design exposes a small, validated KPI pack per business domain so that users can ask a question and then pivot into the surrounding operational context.

Commercial / Sales
  • Net sales, gross margin and sales growth
  • Top customers, top materials and low-performing segments
  • Plan vs actual, forecast attainment and returns
  • Primary and secondary sales where applicable
Supply chain / Inventory
  • Current stock, days of cover and aging stock
  • Stockout risk, blocked stock and warehouse fill rate
  • Inbound pipeline, replenishment requirements and service levels
  • Slow-moving and non-moving material visibility
Procurement / Operations
  • Open purchase orders and overdue items
  • Supplier lead time and delivery performance
  • Open STOs, inbound/outbound movement and exceptions
  • Operational backlog and unresolved exceptions
Finance / Management
  • Receivables aging, collections and overdue exposure
  • Budget vs actual and cost center variance
  • Cash-impact indicators linked to sales and procurement
  • Executive summary KPIs with drill-to-detail links

The KPI pack should stay intentionally curated. The agent works best when it can recommend the next logical question—for example, a sales answer can suggest margin, customer mix, stock position, or collection exposure instead of leaving the user with a single isolated number.

The same architecture can serve sales, procurement, supply chain, finance, and other domains, provided each use case has an approved semantic contract and authorization rules.

Two ways to connect enterprise data

Datasphere-centric (recommended for this design): replicate or federate the necessary SAP S/4HANA and non-SAP data into Datasphere models, maintain metric definitions there, and expose an approved analytic model or view through the consumption interface.

Hybrid: access Datasphere for curated cross-system analytics while calling a source-native S/4HANA API for selected operational questions. Treat that connector as a separate policy-controlled tool; do not assume its source-level authorization, freshness or semantics match Datasphere.

3. The semantic layer comes before the LLM

The most important design decision is to define what each business metric means before exposing it to an AI service. The model can translate questions; it must not invent aggregation rules, currency conversion, business calendars, record status logic or row-level access.

SEMANTIC LAYERS — SOURCE TO BUSINESS QUESTION
AI contractApproved metric names, business synonyms, filters, groupings, units and source asset IDs
ConsumptionGoverned analytic models / exposed views selected for external access
Business semanticsNet sales, open quantity, exceptions, time logic, currency and hierarchies
ModelingFact grain, dimensions, associations, calculated/restricted measures and master data
IntegrationReplicated / federated source entities, transformations and harmonized keys

The AI contract is maintained in the application layer. It references approved Datasphere assets rather than replacing their semantics.

Example metric contract

APPLICATION-LEVEL CONFIGURATION — ILLUSTRATIVE JSON
{
  "metric_id": "net_sales",
  "label": "Net Sales",
  "definition": "Sales net of approved returns and discounts",
  "source_asset": "AM_SALES_PERFORMANCE",
  "measure": "NetSalesAmount",
  "default_currency": "USD",
  "date_dimension": "PostingDate",
  "allowed_dimensions": ["Region", "Customer", "Month"],
  "allowed_filters": ["Region", "PostingDate"],
  "max_rows": 100,
  "owner": "Sales Analytics"
}

The names and fields are illustrative. In production, verify the precise analytic model and OData metadata, including the supported query syntax and measure annotations. The registry should be reviewed together with the Datasphere model whenever a metric definition changes.

Semantic controls that prevent wrong numbers

  • Grain: identify whether a model represents invoice items, orders, daily snapshots or another business grain; prevent double counting.
  • Aggregation: distinguish additive amounts, distinct counts, stock snapshots and ratios; do not SUM a pre-calculated percentage.
  • Dimensions: enforce permitted groupings and correct associations; handle orphan keys and text lookups.
  • Time: define posting date versus document date, fiscal calendar, partial periods and comparisons.
  • Units and currencies: expose a unit with each quantity or amount; never silently mix currencies.
  • Business definitions: store exclusions such as canceled documents, delivery-completed orders or rejection codes in the governed model where possible.

4. SAP Datasphere API and data retrieval

SAP Datasphere provides consumption APIs for exposed views and analytic models. It is important to distinguish relational data retrieval from analytical queries: the API capabilities, URL paths and query options are not interchangeable. SAP documents OData v4 support with restrictions, pagination and rate limits. Official OData API documentation.

  1. Create the consumption asset

    Use an analytic model for analytical metrics where supported, or a view explicitly exposed for consumption when relational retrieval is needed.

  2. Deploy and inspect metadata

    Generate the request from the Datasphere editor and inspect its service metadata. Avoid guessing API paths or measure names.

  3. Choose an OAuth flow

    Decide whether the request uses an individual effective identity or a technical OAuth client, based on the authorization requirement.

  4. Implement a dedicated API adapter

    Keep token acquisition, parameter serialization, retry logic, pagination and response parsing outside the LLM prompt.

  5. Return a bounded typed result

    Map API data to a small result contract containing measure, period, grouping, unit, filters and source reference.

SERVICE PREFIX — FORMAT DOCUMENTED BY SAP
GET https://<tenant-host>/api/v1/datasphere/consumption/<request>
Authorization: Bearer <access-token>

The remainder of the route depends on whether you are retrieving analytical or relational data. Generate the exact URL and query from your tenant's editor, then restrict it in the backend to approved assets. The deprecated /api/v1/dwc/consumption/ prefix should not be used for new integrations.

Read-only boundary: SAP documents the Datasphere consumption OData API as read-only. An agent that performs transactions—such as approving an order or updating a sales document—needs a separate, authorized write-capable business API and explicit action controls. Do not suggest that OData consumption itself updates business data.

Why tool calling is safer than unrestricted text-to-SQL

Text-to-SQL may be appropriate for narrow, validated use cases, but an enterprise analytics agent should not execute unreviewed model-generated SQL against production Datasphere. A constrained analytical tool registry reduces query ambiguity, limits schema exposure, and permits deterministic tests. Parameterized filters, fixed templates and verified semantic models remain authoritative.

6. Tool registry and orchestration implementation

A tool is a backend function the LLM is allowed to request. It should have a clearly defined JSON schema and server-side validation. Three typical tools are get_kpi, get_metric_breakdown, and compare_periods. More tools can be added for rankings, trends and carefully bounded detail tables.

APPROVED TOOL INPUT — ILLUSTRATIVE
{
  "tool": "get_metric_breakdown",
  "args": {
    "metric_id": "net_sales",
    "group_by": "Region",
    "period": "2026-10",
    "top": 10
  }
}
SERVER-SIDE VALIDATION — TYPESCRIPT PSEUDOCODE
async function executeMetricTool(request, session) {
  const contract = registry.get(request.metric_id);
  if (!contract) throw new Error('UNKNOWN_METRIC');

  authorize(session, contract.asset, request.group_by);
  validatePeriod(request.period);
  validateGrouping(contract.allowed_dimensions,
                   request.group_by);
  const limit = Math.min(request.top ?? 10,
                         contract.max_rows);

  return await datasphereAdapter.query({
    asset: contract.source_asset,
    measure: contract.measure,
    groupBy: request.group_by,
    period: request.period,
    limit,
    identity: session.datasphereIdentity
  });
}

The connector implementation must use the supported API and OAuth approach appropriate to the deployed tenant. The sample above is orchestration pseudocode, not a complete SAP Datasphere SDK or deployable integration package.

MCP is optional, not the database access protocol

The Model Context Protocol (MCP) can provide a standard interface for registering approved analytics tools and exposing them to an AI client, but it is not a replacement for Datasphere OData, OAuth authorization or metric validation. An MCP server would wrap the same governed backend functions, enforce authentication and authorization, and return typed results. A straightforward application can use native LLM function calling without introducing MCP. Choose the protocol based on interoperability needs rather than adding it for its own sake.

Prompt and response boundaries

  • System instructions: establish the assistant's purpose, tool restrictions, clarification policy and refusal behavior.
  • Business catalog: deliver only relevant definitions and field metadata; avoid sending all tenant schema metadata to the model.
  • Tool result: mark data as untrusted content and distinguish values from instructions embedded in customer names or comments.
  • Answer generator: compute totals, percentages and comparisons outside the model when deterministic calculations are possible.
  • Response renderer: show the business question, filters, metric definition, number formatting, chart, data timestamp and provenance.

7. Controlling the AI: identity, DAC and least privilege

The AI model is not the security enforcement point. Security must be enforced in the identity service, application authorization layer, Datasphere consumption privileges and Data Access Controls (DAC) where applicable. SAP defines DAC permissions as mappings between effective Datasphere users and allowed criteria. Official DAC documentation.

ControlPurposeEnforcement location
AuthenticationKnow who is making the request.Corporate IdP / application gateway.
App authorizationWhich users can request which tools, metrics, and business domains?Backend policy service.
Datasphere accessRestrict accessible spaces/assets through scoped roles and OAuth.SAP Datasphere.
Row-level securityReturn only permitted records.DAC on supported governed assets.
Query controlsLimit dates, dimensions, rows, frequency and expensive requests.Tool registry + API adapter.
Prompt safetyPrevent instructions in data from overriding business rules.Orchestrator + LLM input handling.
Data exposureMinimize data sent to LLM providers and logs.Data handling and privacy policy.

Critical point: technical identity is not the end user

If the backend authenticates to Datasphere with a single technical OAuth client, Datasphere evaluates the authorization for the effective identity associated with that client. DAC does not automatically change based on the web application's logged-in user. Two users routed through the same technical client can therefore receive the same underlying Datasphere permission scope unless the application imposes additional restrictions.

For identity-specific access, evaluate an SAP-supported user-propagation pattern (for example an appropriate interactive or trusted principal-propagation flow), verify the effective Datasphere principal, and test DAC results for multiple users. For service-to-service access, use a restricted technical identity and enforce application-side authorization, with separate credentials or assets where necessary.

Never trust an LLM-generated filter as an access control. $filter=Region eq 'North' is a query condition, not a substitute for server-side policy or DAC. Do not present results as per-user secure until the effective identity and permissions have been verified in end-to-end tests.

Multi-tenant and multi-company isolation

For an application that supports multiple companies or business units, isolate configuration and runtime state by a verified tenant identifier. Bind each tenant to its approved Datasphere space, asset catalog, OAuth setup and semantic registry; never accept a tenant or asset identifier supplied solely by the LLM. Treat shared caches, conversation memory, retrieved metadata and logs as potential leakage paths. An authorized user in tenant A must not be able to retrieve a cached response or catalog definition belonging to tenant B.

Other safeguards

  • Store credentials in a secrets manager; do not put OAuth secrets or Datasphere connection details in the browser or prompt.
  • Permit only read-only, approved metrics and enforce network egress rules.
  • Scrub or minimize personal data before sending prompts or retrieved records to external model services.
  • Partition conversation history, cache keys and logs by tenant, user/security context and authorized asset.
  • Apply token, time and row budgets to protect against runaway execution and data exfiltration.
  • Require confirmation and a separate approval control before any future write action is permitted.

8. Development environment and reference stack

This architecture is vendor-neutral on the language model. A realistic implementation can be built with React / Vite for the web interface and Node.js / TypeScript for the backend and orchestration. The model service could be a supported enterprise LLM provider or managed AI gateway; choose it based on residency, contractual data-use controls, latency and security requirements. These technologies are example choices, not prerequisites imposed by SAP.

9. Implementation sequence

  1. Define 10–20 validated business questions

    Agree on metrics, filters, expected results, currency, date logic, users and authorized data scope. Record baseline answers from a trusted report.

  2. Prepare the source and data integration

    Set up supported SAP S/4HANA or other source connections; choose replication versus federation based on freshness, load and source constraints.

  3. Build and govern Datasphere models

    Create facts, dimensions, associations and analytic models. Apply business definitions and validate reconciliation against source figures.

  4. Secure and expose approved consumption assets

    Assign scoped roles, DAC where applicable, expose the view or analytic model, generate service requests and test OAuth permissions.

  5. Create the semantic registry

    Register business metric IDs, source asset names, permitted fields and filters. Version the contracts.

  6. Implement the API adapter and tool gateway

    Write deterministic OData query generation, typed response mapping, authorization and bounds checking.

  7. Integrate an LLM for intent/tool selection

    Make the model ask clarifying questions for ambiguous periods, KPI definitions or missing required parameters.

  8. Build the frontend experience

    Use KPI cards, charts, comparison views, drill-through links, source timestamps and transparent error messages.

  9. Run security and answer-quality tests

    Test correct/incorrect metrics, DAC identities, prompt injection, missing data, date boundaries and request limits.

  10. Deploy, monitor and iterate

    Track latency, cost, retrieval quality, token usage, freshness and unanswered business questions.

Accuracy scorecard

Build a regression set covering totals, top-N rankings, time comparisons, authorization differences and negative test cases. For each question, capture the expected metric contract, approved result, allowable tolerance, required output fields and whether the agent should ask a clarification rather than answer. Assess both retrieval correctness and explanation fidelity: an accurate numeric value with the wrong currency, period or grouping is still a failed response.

Operational signals

Track the end-to-end request ID, API response status, semantic contract version, data product, principal, duration, token/cost budget and freshness status. Record only data needed for support and audit; mask sensitive fields and apply retention controls. A successful HTTP call is not evidence that the metric is correct—run regression tests against independently validated figures.

What the agent should say when it cannot answer

Distinguish data not available, not authorized, unsupported analytical question and temporary technical failure. Never fill missing business data with model-generated estimates unless the product clearly labels a separate, authorized forecasting function.

11. Design choices and trade-offs

ChoiceBenefitTrade-off / risk
Curated metric toolsPredictable results; easy authorization and regression testing.New metrics require registration and review.

Analytic modelsBusiness-oriented measures and dimensions.Must use analytical API syntax and supported semantics correctly.
Exposed relational viewsControlled row retrieval.Aggregation semantics may need more application logic.

Per-user principal propagationStronger alignment with user-specific Datasphere authorization.More involved identity trust and token flow configuration.

There is no single deployment topology suitable for every enterprise. The core design stays consistent: approved data products + effective-identity security + constrained analytical tools + auditable results.
